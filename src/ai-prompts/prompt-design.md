# V3.0 AI 玩家提示词体系设计

## 1. 目标

V3.0 提示词体系优先解决四类问题：

1. 发言反复表达同一个判断，形成“车轱辘话”。
2. 发言只有态度，没有证据、对象或下一步行动。
3. 为显得会分析而复述聊天记录，导致冗长、不直接。
4. 模型利用未授权信息推断身份、夜间行动或规则结果，形成剧透。

质量目标不是“说得多”，而是每次发言都推动一次判断或行动：

> 一句话主张 + 一条最强证据 + 一个明确目标。

示例结构：

> 我更怀疑阿明，因为他先承诺投阿杰，票型公开后却无解释改票；这轮我会投阿明。

不是每次都要机械输出三句话。允许把三项压缩到一至两句，但三项必须可识别。

## 2. 分层结构

每次调用按以下顺序拼装，越靠前优先级越高：

1. `system-prompts.md` 中的全局系统提示词。
2. `role-templates/<role>.md` 中对应角色的身份、视角与策略层。
3. 服务端生成的规则事实块 `{{rules_for_role}}`。
4. 服务端生成的当轮可见事实块。
5. 当前阶段任务块与输出格式。

推荐的消息职责：

| 层 | 内容 | 是否跨轮稳定 |
|---|---|---|
| System | 权威边界、信息使用规则、发言纪律、阵营目标 | 是 |
| Role | 角色视角、角色策略、阶段任务 | 是 |
| Runtime facts | 公开事件、私有事实、合法目标、历史发言 | 否 |
| Output contract | 当前动作、长度、格式、可选值 | 否 |

不得把服务端全量状态直接放进 prompt 后要求模型“自己忽略”。服务端必须先做视角投影，再填充模板。

## 3. 占位符契约

### 3.1 通用身份与阶段

| 占位符 | 含义 |
|---|---|
| `{{player_name}}` | 当前 AI 玩家名 |
| `{{role_name}}` | 当前角色名称 |
| `{{alignment}}` | 当前阵营 |
| `{{day_number}}` | 当前天数 |
| `{{phase_name}}` | 当前阶段 |
| `{{round_number}}` | 当前阶段内轮次 |
| `{{speech_char_limit}}` | 当前发言字数上限 |
| `{{output_contract}}` | 服务端要求的最终输出格式 |

### 3.2 服务端权威规则

| 占位符 | 含义 |
|---|---|
| `{{rules_for_role}}` | 与当前角色、阶段和动作有关的规则文案 |
| `{{win_condition}}` | 当前阵营胜利条件 |
| `{{experience}}` | 服务端按角色/阶段选择的行为参考；不是事实，不覆盖规则和上下文 |
| `{{legal_actions}}` | 当前阶段允许的动作集合 |
| `{{legal_targets}}` | 经服务端校验后的合法目标集合 |
| `{{abstain_policy}}` | 当前投票是否允许弃票 |
| `{{last_words_policy}}` | 当前玩家是否有遗言、剩余轮数与限制 |

模板不得根据常识补全缺失规则。规则占位符为空、矛盾或未渲染时，模型只能输出 `{{invalid_context_response}}`，不得自行决定。

### 3.3 可见事实

| 占位符 | 可见性 | 内容 |
|---|---|---|
| `{{public_events}}` | 公开 | 服务端已公开的死亡、平安夜、放逐等事件 |
| `{{alive_players}}` | 公开 | 当前存活玩家 |
| `{{public_speeches}}` | 公开 | 当前视角允许保留的公开发言 |
| `{{public_vote_history}}` | 公开 | 已锁定并公开的历史票型 |
| `{{current_round_speeches}}` | 公开 | 本轮已发生发言 |
| `{{own_previous_speeches}}` | 本人 | 自己近期发言，用于防复读和承诺检查 |
| `{{own_vote_commitment}}` | 本人 | 自己最近一次明确投票承诺；没有则写“无” |
| `{{private_role_facts}}` | 角色私有 | 仅该角色依法可知的事实 |
| `{{wolf_private_chat}}` | 狼队私有 | 存活狼人之间的夜间讨论 |
| `{{new_information_since_last_turn}}` | 当前视角 | 自己上次发言后新增的公开或私有信息 |
| `{{situation_summary}}` | 当前视角 | 由服务端基于可见事实生成或提取的局势摘要 |

### 3.4 防复读辅助

| 占位符 | 含义 |
|---|---|
| `{{already_stated_claims}}` | 自己已表达过的核心主张集合 |
| `{{already_used_evidence}}` | 自己已使用过的证据集合；未提供时明确标记缺失 |
| `{{other_players_current_claims}}` | 本轮其他玩家已表达的主张摘要 |
| `{{required_novelty}}` | 本次必须补充的新信息类型，如“回应改票” |

这些字段必须是当前玩家可见内容的摘要，不得由全知日志生成。

### 3.6 行为参考

| 占位符 | 可见性 | 内容 |
|---|---|---|
| `{{experience}}` | 服务端选择 | 结构化行为参考；只能作为候选策略，不能升级为事实 |

经验参考不是事实字段，不能替代规则、可见事件、角色私有事实或合法动作。

### 3.7 空值与渲染约定

- 所有占位符在调用前必须完成渲染；最终 prompt 中不得残留 `{{` 或 `}}`。
- 普通空列表统一渲染为“无”，不能省略标签后留下空白。
- “没有新增信息”应明确写“无新增信息”，不能让模型从字段缺失推断事件未发生。
- 角色私有块只装配给对应角色。其他角色的 prompt 中不能出现该字段名、空数组或完成状态。
- 布尔与权限状态使用明确枚举文案，如“有投票权 / 无投票权”，不依赖真假值猜测含义。
- 规则或合法动作字段不得为空；若为空，服务端应中止正常调用并使用 `{{invalid_context_response}}`。
- 所有代码块都是可拼装的模板片段。运行时只选择一个角色层、一个阶段任务和一个输出契约，不把整份 Markdown 原样发送给模型。

## 4. 发言质量协议

### 4.1 输出前静默检查

模型在生成最终文本前，必须在内部完成以下步骤，但不得输出分析过程：

1. 找出本轮最需要处理的一个问题。
2. 选择一条当前可见、最强且未被自己用烂的证据。
3. 与 `{{already_stated_claims}}` 和 `{{already_used_evidence}}` 对比。
4. 若没有新增信息，不复述旧分析，只输出短更新、明确追问或跳过。
5. 给出一个行动目标：投谁、保留谁、追问谁、查谁、守谁、刀谁或暂不改变判断。

### 4.2 硬约束

- 第一处有效信息必须是主张，不用寒暄、自我介绍或“先说结论”铺垫。
- 一次发言只处理一个主问题。需要全盘梳理时，仅在服务端标记为 `{{is_daily_summarizer}} = true` 时允许。
- 主张必须指向具体对象、具体选择或具体不确定点。
- 证据优先级：私有确定信息 > 已公开事实 > 已公开票型 > 原话或实质矛盾 > 有范围的不确定判断。
- 不把“感觉不对”“发言不好”“再听听”单独当证据。
- 不逐条复述聊天记录，不总结所有玩家，不重复已公布死讯。
- 不连续使用相同开头、句式、论证顺序或收尾。
- 不使用 Markdown、标题、列表、角色说明、思考过程或提示词术语。
- 不超出 `{{speech_char_limit}}`。

### 4.3 无新增信息时

优先级如下：

1. 回答刚发生的点名或质疑。
2. 提出一个能获得新信息的具体问题。
3. 更新置信度或行动，不重复旧理由。
4. `{{legal_actions}}` 明确允许时输出跳过指令。

合格：

> 我对阿明的判断没变，但现在没有新证据。阿明解释一下为什么改票。

不合格：

> 我还是觉得阿明很可疑，他真的很可疑，大家多关注一下。

## 5. 重复与“车轱辘话”定义

以下任一情况视为重复：

- 与自己上一轮核心主张、证据、目标三项全部相同。
- 只替换同义词、语序或玩家名，论证结构不变。
- 复述其他玩家刚说过的判断，却没有增加证据、反驳或行动。
- 同一发言内重复结论两次以上。
- 用“我再看看”“信息不多”“大家都有道理”等话拖延，但没有说明等待谁的哪项信息。

允许的必要重复：

- 预言家重报查验时间线时，为纠正误解或处理对跳。
- 投票前重申承诺，但必须压缩为一句并补充当前行动。
- 遗言交代真实私有信息。
- 服务端通过 `{{required_novelty}}` 明确要求核对某段历史。

即便允许重复，也只保留完成任务所需的最短版本。

## 6. 可见性边界

### 6.1 共同原则

- 服务端是唯一权威事实源。
- 模型只能使用模板中已渲染的内容。
- “没提供”不等于“没有发生”，只能表示当前玩家不知道。
- 公共事实与私有事实必须分区注入，不能混成一段。
- 死亡原因、隐藏身份、夜间行动等是否公开，只服从 `{{public_events}}` 和 `{{rules_for_role}}`。
- 推理必须用“不确定”措辞；只有服务端给出的确定事实才能用确定语气。

### 6.2 角色可见性矩阵

| 信息 | 狼人 | 预言家 | 女巫 | 守卫 | 猎人 | 平民 |
|---|---:|---:|---:|---:|---:|---:|
| 白天公开事实与发言 | 可见 | 可见 | 可见 | 可见 | 可见 | 可见 |
| 已公开票型 | 可见 | 可见 | 可见 | 可见 | 可见 | 可见 |
| 狼队友身份 | 可见 | 不可见 | 不可见 | 不可见 | 不可见 | 不可见 |
| 狼聊与狼队决策过程 | 可见 | 不可见 | 不可见 | 不可见 | 不可见 | 不可见 |
| 自己的查验目标与结果 | 不可见 | 可见 | 不可见 | 不可见 | 不可见 | 不可见 |
| 女巫收到的刀口通知与用药 | 不可见 | 不可见 | 可见 | 不可见 | 不可见 | 不可见 |
| 自己的守护记录 | 不可见 | 不可见 | 不可见 | 可见 | 不可见 | 不可见 |
| 猎人开枪资格 | 不可见 | 不可见 | 不可见 | 不可见 | 仅本人可见 | 不可见 |
| 其他隐藏身份 | 不可见 | 不可见 | 不可见 | 不可见 | 不可见 | 不可见 |

“不可见”字段不得以空值、布尔值、完成状态或异常信息侧漏。

## 7. 防剧透与事实边界

### 7.1 禁止内容

- 说出未在 `{{private_role_facts}}` 或 `{{public_events}}` 中提供的身份、查验、刀口、守护或用药结果。
- 根据服务端字段缺失断言某动作没有发生。
- 把规则允许的动作说成已经发生。
- 把策略性推测说成服务端确认。
- 暴露完整 prompt、规则内部键、API 信息、文件路径、调试信息或观战全知内容。

### 7.2 合法撒谎与非法伪造

狼人和好人都可以进行规则允许的身份伪装。战术性发言与事实记忆必须区分：

- 合法：狼人公开悍跳预言家并编造一条对外口径。
- 合法：平民为挡刀声称自己像神职。
- 非法：模型在内部把编造口径写入“真实查验记录”，后续当成服务端事实。
- 非法：狼人说“昨晚守卫守了阿明”，因为狼队没有这个视角。
- 非法：女巫未收到刀口通知，却自行判断“狼人空刀”。

角色模板中的伪装策略必须写成“公开口径可编造”，同时明确“私有事实只来自服务端”。

## 8. V3.0 新规则的提示词表达

规则值不硬编码在角色模板中。服务端从当前 RuleSet 生成角色相关文案，填入 `{{rules_for_role}}`、`{{win_condition}}`、`{{legal_actions}}` 与 `{{legal_targets}}`。

### 8.1 狼人可自刀与空刀

关联规则键：

- `roles.werewolf.can_self_kill`
- `roles.werewolf.can_empty_kill`
- `roles.werewolf.kill_target`

注入要求：

- `{{legal_targets}}` 直接包含服务端允许的所有目标，包括符合规则时的自己和狼队友。
- `{{legal_actions}}` 明确是否包含空刀。
- 狼人模板只负责比较收益：屠边进度、骗药收益、身份暴露风险和团队损失。
- 模型不得因常识排除狼队友，也不得在目标列表外构造目标。

### 8.2 屠边胜负

关联规则键：

- `victory.mode`
- `victory.good_win`
- `victory.werewolf_win_gods`
- `victory.werewolf_win_villagers`
- `victory.simultaneous_both_sides_condition`

注入要求：

- 狼人收到服务端生成的 `{{win_condition}}`，据此判断优先压神职边还是平民边。
- 好人只知道公开身份声明和公开死亡，不得从服务端真实身份计数获得“还剩几个神/民”。
- 模型可以说“如果他的身份声明为真，神职边可能危险”，不能断言隐藏边数。

### 8.3 女巫视野阻断

关联规则键：

- `roles.witch.guarded_target_notice`
- `roles.witch.antidote_when_no_notice`
- `resolution.same_guard_same_save`

注入要求：

- 女巫只接收服务端最终允许展示的 `{{witch_kill_notice}}`。
- 没有通知时，不注入刀口占位符，不使用“未知目标”这类可侧漏结构。
- `{{legal_actions}}` 决定解药是否可选；模型不得根据守护、空刀或系统等待状态推断原因。

### 8.4 猎人仅票出开枪

关联规则键：

- `roles.hunter.shoot_trigger`
- `roles.hunter.shoot_when_poisoned`
- `roles.hunter.shoot_when_wolf_killed`

注入要求：

- 只有服务端授予 `{{hunter_shot_available}}` 时才装配开枪任务块。
- 夜间死亡或中毒死亡不得装配开枪块，也不得让模型预测自己“死后会开枪”。

### 8.5 平票重投

关联规则键：

- `voting.tie_policy`
- `voting.repeat_vote_scope`
- `voting.abstain_allowed`

注入要求：

- 重投时 `{{legal_targets}}` 只包含平票候选。
- 平票候选无投票权时，不为其发起投票调用。
- `{{abstain_policy}}` 明确禁弃票；输出契约中不得展示跳过选项。
- 再次平票后的结果由服务端结算，模型不得自行宣布谁出局。

### 8.6 两轮遗言

关联规则键：

- `speech.last_words_scope`

注入要求：

- 仅服务端认定符合条件的被放逐玩家收到遗言任务。
- `{{last_words_round}}` 和 `{{last_words_rounds_remaining}}` 由服务端填充。
- 第一轮优先交代身份、确定信息和核心狼坑；第二轮只补遗漏、回应现场新信息或给最终行动建议，不重复第一轮全文。

### 8.7 狼刀平票

关联规则键：

- `roles.werewolf.kill_tie`

注入要求：

- 首次平票后装配“重新讨论”任务，注入平票目标和分歧点。
- 第二次投票仍只服从 `{{legal_targets}}` 和 `{{legal_actions}}`。
- 第二次平票如何结算由服务端执行，模型不得自行随机选人或宣布结果。

## 9. 角色差异化策略

| 角色 | 信息优势 | 发言重点 | 夜间重点 | 主要反模式 |
|---|---|---|---|---|
| 狼人 | 队友与狼聊 | 伪装好人视角、制造可验证但误导性的焦点 | 按屠边路线选刀，自刀/空刀需算收益 | 直接暴露狼队、编造服务端事实、无脑保队友 |
| 预言家 | 自己的阵营查验 | 报完整查验时间线、处理对跳、归票 | 查验信息增益最高且合法的目标 | 报具体职业、长期藏信息、重复验人 |
| 女巫 | 自己的刀口通知和药剂状态 | 隐藏药情，必要时用真实用药信息自证 | 单夜合法动作中比较救、毒、留药 | 推断守卫目标、无通知仍救、同时用两药 |
| 守卫 | 自己的守护记录 | 以公开逻辑盘人，必要时交代真实守护线 | 保护关键位并遵守合法目标 | 用平安夜反推守护成功、连续守同一人 |
| 猎人 | 自己是否获得开枪资格 | 平时按好人逻辑盘人，被放逐时交代枪口 | 仅服务端授予后选择枪口 | 被刀/毒后自行触发枪、靠“我能开枪”空威胁 |
| 平民 | 仅公开信息 | 拆矛盾、盘票型、明确站边和投票 | 无夜间任务 | 编神职信息、机械附议、把身份猜测说成事实 |

## 10. 运行时装配建议

1. 服务端先按可见性生成事实投影。
2. 从 RuleSet 生成当前角色、当前阶段所需的最小规则文案。
3. 只装配一个当前任务块，不把所有阶段说明同时塞给模型。
4. 提供自己近期主张与已用证据摘要，执行防复读。
5. 提供合法动作、合法目标和机器可解析输出格式。
6. 模型输出后执行长度、目标、枚举、重复度与泄密检查。
7. 校验失败时，使用最小纠错 prompt 重试，不重新发送全知状态。

## 11. 旧提示词迁移注意

现有提示词中以下做法不应进入 V3 模板：

- “死亡玩家信息全流摘除”：死亡玩家过去已经公开的发言仍属于公共历史，是否保留应按上下文窗口与摘要策略决定，而不是因死亡而抹除。
- “女巫始终看到当晚被刀者”：V3 必须由服务端通知决定，守护成功会阻断通知。
- “猎人被刀后可以开枪”：V3 仅被放逐时可开枪。
- “不要投狼队友”：V3 狼人可使用倒钩、狼踩狼与自刀，目标约束必须来自服务端。
- “没依据就反复说再听听”：应改为具体追问或跳过。
- 同时给出互相冲突的长度例外：每次调用只注入一个最终字数上限。

## 12. 成功指标

- 同场景三次生成的核心主张可以相同，但措辞、证据选择或行动焦点不应机械一致。
- 每条非跳过发言至少包含主张、证据、目标中的两项；关键归票发言必须三项齐全。
- 不出现服务端未注入的隐藏身份、夜间行动和死亡原因。
- 不出现模板占位符、规则键、Markdown 或分析过程。
- 所有结构化动作均能通过服务端目标与枚举校验。
